## Trigger

用户抛出「一道算法题」（判断质数、滑动窗口、DP、单调栈等），先要答疑/讲解，最后可能沉淀成博客。典型开场：「有一道算法题…最粗暴的解法我做出来了，可是到 N 怎么优化」。

**两种入口，走不同子模式：**
- 入口 A「怎么从 N 优化到更快」→ 走下面的「教学顺序」（渐进优化阶梯）。
- 入口 B「我写的代码错在哪 / 提交挂了 / 帮我看看有什么问题」→ 走「子模式 B：对拍定位法」。**不要用 A 的方式回答 B**。

## 教学顺序（用户强偏好：先让他学会，产出是副产品）

1. **先讲透概念，再给代码**。用户第一诉求是「学会」，不是要成品代码。
2. **用「渐进优化阶梯」叙事**组织讲解，而非知识点罗列：
   `最笨解法 → 逐个剪枝(search space / 复杂度逐级下降) → 思维反转(最优)`
   每一步贴三件套：**思路 + 复杂度(量级) + 真实数值实例**。
3. **一定实际跑代码验证**，不是空讲。把每级解法写出来跑，得到真实耗时/数值对比表（build 后报告真实数字）。「改进是否真快」要用实测 `time` 数据支撑，别说「理论上更快」。
4. 复杂度讲法：区分**量级提升**（O(n)→O(√n)）和**常数优化**（O(N^1.5)→O(N^1.5/lnN)，量级没变），诚实说明后者追不上量级提升。
5. 用**数值实例**讲原理（如 n=97 试到 √97≈9.8 只需 2,3,5,7），别堆抽象证明。
6. **反馈闭环（必做）**：每讲完一个层级/概念，主动引导用户用自己的话输出（总结/举例/画流程/预判下一步），再用开放式问题（非「懂了吗」）逼他复述；对照他的输出逐个纠正偏差点（指出「你说的 X 不对：正确是 Y」），点出答对背后的关键洞察；纠正后的正确认知随手记下，作为博客/知识库候选素材。未输出前不要急着进下一层。

## 子模式 B：答疑 / 调试用户自己的错误提交（对拍定位法）

用户贴出自己写错的代码问「有什么问题」时，**禁止肉眼读代码就下结论，也禁止直接甩一版正确答案**——他要的是定位 + 学会。流程：

1. **对拍定位，不靠眼力**。把用户每个版本原样抄进一个脚本（骨架见 `templates/diff_test_harness.py`），跑随机用例 + 手工边界用例，拿到**失败率**。失败率是严重度排序的客观依据：「最新版 2978/3961 失败、上一版 650/3961」比「我觉得这里有问题」有力一个量级。
2. **对拍三件套**：① `brute()` 用 `sorted(a+b)` 之类的朴素暴力参考解；② 随机**小规模**用例（长度 0~9、值域窄 → 边界碰撞率高）；③ 手工边界用例（空数组、单元素、两数组长度悬殊、全相等、交错）。边界用例常抓到随机用例抓不到的越界。
3. **加死循环护栏 —— 首选「步数计数器」，别用 setitimer 逐用例设闹钟**：在被测代码的 `while` 入口插 `steps += 1; if steps > 200: raise Timeout`。实测教训：用 `signal.setitimer(..., 0.3)` 逐用例包住调用，遇到大量死循环用例时（V5 有 1344 个）每个都吃满 0.3s，5000 用例直接把对拍拖过 **300s 工具超时**，白跑一轮；步数计数是纯 Python 整数比较，开销可忽略。setitimer 只留作 **1s 粗兜底**。
4. **最小反例 + 逐步 trace**：每个 bug 定位后单独写 trace 脚本，逐轮打印 `k / indx1 / indx2 / 判据 / 淘汰量`，讲解时直接贴 trace（配「期望=X 实际=Y」）。比抽象描述有效一个量级。
5. **逐个隔离，一次只修一个**：多 bug 叠加时，修一个重跑一次对拍看失败率变化。这能证明「边界修好后仍错 1065/5943」→ 说明那不是手滑而是**判据本身错了**，必须补正确性证明。
6. **区分「手滑」和「思路错」**：笔误、变量名/索引写错一句带过；思路错要给不变量 + 最小反例 + 证明。别把两者混为一谈，用户会以为改个字符就完了。
7. **收尾走反馈闭环**：让用户拿最小反例自己走一遍正确算法，并**口头证明「为什么这些元素能被淘汰 / 不可能被淘汰」**，再对照纠偏。未输出不进下一层。

### 讲解骨架（错误提交版）

`一句话结论（哪几层错、最致命的是哪层）` → `先立正确性铁律 / 不变量` → `按严重度分层列 bug：错在哪 + 最小反例 + 真实 trace + 失败率` → `一句带过的小瑕疵（返回类型 / 风格）` → `开放式问题让用户复述+证明`。

## 子模式 C：引入第二解法并实测对比

用户说「这里还有另一种解法，一并介绍一下」（常见于官方题解有多解）时。详见 `references/solution-comparison-benchmarking.md`。

1. **先抓官方原文**（web_extract 题解页），别凭记忆写第二解法——推导细节记错会讲出错误的原理。
2. **自己转写成目标语言并跑通 + 对拍**（`brute()` + 随机 + 边界，要 0 失败）。转写官方代码后不验证就贴进文章 = 把未验证代码当结论。
3. **对比优先用确定性计数器（循环轮数 / 比较次数），挂钟微秒只作补充**：同量级算法在 μs 尺度上挂钟全是噪声，多跑几轮也压不住。LC4 实测轮数：两数组各 100 万 → 方法一 42 轮 vs 方法二 19 轮；而 `1 vs 100万` → 方法一只要 **2 轮**（短数组迅速耗尽 → 提前返回）。
4. **量化常数差异的结构性原因**，别只说「常数不同」：LC4 方法一偶数总长要跑**两遍** `getKthElement`（k 与 k+1 各一次，无法复用），42 ≈ 2×21 就是这么来的。
5. **对比表必须配一个「反直觉点」**（用户认可的行文习惯）：如「`m << n` 时方法一轮数反而远少于方法二，`log min(m,n)` 的优势根本体现不出来」——诚实的反面数据比一边倒吹最优解可信得多。
6. 收尾按 **复杂度量级 → 常数实测 → 适用场景选择表**（照 `zacharyxue-blog` 的「怎么选」表格范式）。

## 转博客文章时

- 先给**章节级架构/提纲**让用户认可，再写正文（参照 zacharyxue-blog skill 的写作铁律）。
- **算法题文章骨架（用户 2026-10 明确定长）**：`题目` → `常规解` → `另一种解` → `我失败的逻辑（复盘细节）`。用户原话：「先按正常思路解，然后附上这里另外的思路，最后再从我失败的逻辑来讲细节」。
  - `题目` 节**照抄官方题面原文**（题面 + 示例 + 约束表 + 原题链接），不要改写——用户明确要求「先写出题目」。
  - 交付节奏：先给 `提纲 + 题目节草稿` → 用户圈选（篇幅深度 / 示例选哪个）→ 才写正文。
  - **失败复盘是卖点不是附录**（用户要的就是「从我的失败讲细节」），别压缩成一句「注意边界」。
  - 文章标题可带「两种 O(log) 解法 + 我的五种死法」这类**正解 + 踩坑**双主题结构。
- **用户明确说某段「没看懂 / 先不管了」→ 从成品文章坚决砍掉，不要硬塞进去**。现实中：用户跳过 Miller-Rabin，文章就只讲质数筛选（试除→√n→只试已知质数→埃氏筛），结尾一句话带过即可。这是本 skill 最重要的纠偏。
- 结构偏好：**mermaid 阶梯总览图开局** + 图标/表格多、文字少 + 每节 `一句话总结` 收尾 + 结尾真实耗时对比表 + 工具选择表 + 一句话记住。
- 实测数据要复用讲解阶段真实跑出的数字（别重写或编造）。
- 博客仓库/格式/构建验证细节 → 走 `zacharyxue-blog` skill（注意它在 external dir，构建后需 npm run build 验证、commit 不 push）。
- **多版本对拍必须统一口径**：用户常一次贴出「最新版 + 之前几版」求诊断。把各版本放进**同一批用例**跑（固定 seed + 手工边界），失败率才可比；不同用例集上跑出的数字不能并列成表。
- **用户自己写挂的版本是文章资产，比标答更有教学价值**：可作正文主线（如「off-by-one 的 N 种死法」），每版配**最小反例 + 真实失败率**，并归纳到统一模型（本次：看哪/扔几个/减多少 三个量 + 一条红线）。用户说「精选」时按**覆盖不同层次**挑，不按失败率高低挑。
- **复杂度/性能对比优先用「轮数」这类确定性指标**，挂钟耗时只作辅证（受机器噪声影响大）。同时必须解释**反直觉点**（本次：`m << n` 时方法一反而只要 4 轮，`log(min)` 的优势体现不出来），否则表格只是数字堆砌。
- 用户会要求「把官方题解的另一种思路也一并介绍」→ 结构：**题目 → 常规解 → 另一解 → 两法对比 → 我的失败复盘**。另一解要自己转写成可运行版本并实测，不能只抄描述。

## 典型算法知识（可复用原文作参考）

> 每个题型的 bug 分类 + 最小反例 → 写在 `references/<题目-slug>.md`；对拍脚本骨架 → `templates/diff_test_harness.py`；**单 bug 变体注入**（给每个 bug 单独算失败率）→ `templates/variant_injection_harness.py`；多解法对比 + 验证脚本自检 → `references/solution-comparison-benchmarking.md`。已收录：`references/median-of-two-sorted-arrays.md`（LC4 寻找两个正序数组的中位数 —— 三层 bug 分类 + 判据正确性证明）。

- **「淘汰式找第 k 小」三量自洽模型（LC4 及一切二分淘汰类题）**：每轮只做三件事且必须严格自洽 —— `看哪`(pivot 下标 = `indx + t - 1`)、`扔几个`(闭区间长度 = `curr - indx + 1`)、`减多少`(`k -= 真实淘汰数`)。**唯一红线：一轮最多扔 k-1 个**（这就是「减一」的真正价值，不是括号配平）。用户的 4 个错误版本全部栽在这三者之一。核心心法：**k 的减量跟「物理事实」对账，不跟「计划」对账**（被 `min` 夹住时少减才对，硬减 k//2 是谎报战果）。详见 `references/median-of-two-sorted-arrays.md`。

- **判断/筛选质数四级阶梯**：粗暴试除 O(N²) → 试到 √n O(N^1.5) → 只试已知质数 O(N^1.5/lnN) → 埃氏筛 O(N log log N)。要点：因子成对出现(小因子≤√n)、合数除数冗余、筛法从 p² 划+到 √N 停。Miller-Rabin 是另一条线(判断超大单个数)，用户当前不感兴趣。

## Pitfalls

- 别在用户没要求时自作主张写博客文章——先答疑讲解，确认要写再动笔。
- 别用「理论更快」代替真实 benchmark；跑一下时间。
- 用户没掌握的衍生知识点（如 Carmichael 数、Miller-Rabin 二次探测）不要塞进成品文，会稀释主线。
- 用户贴错误代码时，别直接重写一版正确答案贴回去——先诊断定位，最后才（如果他要）给正确写法。
- 死循环类 bug 的定位必须看 trace 里 `k` / 指针的符号。Python 负数整除是向下取整（`-2 // 2 = -1`），指针会**倒退**形成来回震荡的死循环，别以为只是「循环次数多」。
- 「多个版本都错」不等于手滑：三版都踩同一个坑（如判据选错）说明是**理解问题**，必须讲原理，改参数没用。
- 讲算法正确性时，`k`（全局第几小）和 `indx`（本数组内已排除个数）是两个不同量纲，用户混淆它们是高频错误——专门点破。
- 反馈闭环里用户答偏时：**先明确肯定他答对的那半句，再上实测数据指出偏差**（「你说『没有少减』——实测减了 1、`k//2` 是 2」）。要区分「答成了另一个问题」和「答错了」，别一上来否定；用户答对的部分要点出背后的关键洞察（他能指出「curr 自己也要被排除」正是闭区间 `+1` 的前提假设，这就是真的懂了）。
- **验证脚本先自检口径，再信结论**（本次踩了三个坑，刷出来的「39761 次违规」全是假的）：① **统计基准必须和被讨论的量同口径** —— LC4 的 `k` 是相对「剩余元素」的，我却拿**全局合并数组**算排名，口径错位直接产出一堆假违规；② **有重复值时 `bisect_right` 会把同值元素重复计入**，把「值相同的位置本就等价」误判成违规 —— 验「谁不可能是第 k 小」要按值口径，或干脆用无重复值用例（`random.sample`）；③ **自己写进脚本的「期望值」也要核对** —— 曾把 `[1,3,8]+[2,7,9,10]` 的期望误标成 5.5（正确 7.0），差点把两个都正确的实现判成失败。**验证器自身的错误比被测代码的错误更隐蔽，因为它伪装成「被测代码全错」。**
- **资源护栏**：对拍要限制步数防死循环（见子模式 B），benchmark 要限制数组规模——构造超大 `list` 本身就能把工具调用拖过超时（曾用 2000 万元素撞满 300s），复用同一个 list 的切片即可。
- **等价写法不要当成 bug**：官方代码 `min(index + half, len) - 1` 与自写 `min(index + half - 1, len - 1)` 等价，只是 `-1` 位置不同；用户纠结这种写法时要点破等价性，别顺着「哪里减一」陪他钻。
