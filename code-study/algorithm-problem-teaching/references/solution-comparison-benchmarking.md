# 多解法对比与验证脚本自检（以 LC4 为例）

场景：用户已 AC 或即将 AC，要求「一并介绍官方题解的另一种解法」，并要求成文结构为
`题目 → 常规解 → 另一种解 → 我失败的逻辑`。

## 工作流（5 步，缺一不可）

1. `web_extract` 抓官方题解原文。**别凭记忆写第二解法** —— 推导细节记错，讲出来的原理就是错的。
2. 把官方（多为 Java）转写成 Python，跑通。
3. 对拍：`brute()` 暴力解 + 随机小规模 + 手工边界，**要 0 失败**才算转写正确。
4. 对比：**确定性计数器（循环轮数 / 比较次数）为主，挂钟耗时只作补充**。
5. 报告反直觉点 + 适用场景选择表收尾。

## LC4 两解法骨架

| | 方法一：找第 k 小 | 方法二：划分数组 |
|---|---|---|
| 复杂度 | O(log(m+n)) | O(log min(m,n)) |
| 视角 | 反复二分淘汰，逼近第 k 小 | 找一个「切面」，使左右两半等长且左半最大值 ≤ 右半最小值 |
| 关键式 | `curr = min(len-1, indx + k//2 - 1)` | `j = (m+n+1)//2 - i` |
| 边界手段 | `min` 夹取 + 按**实际淘汰数**记账 | `±inf` 哨兵（`i==0 → -inf`、`i==m → +inf`） |
| 偶数总长 | **要跑两遍** `getKthElement`（k 与 k+1） | 单次二分即可，同时拿到 median1/median2 |

划分法的等价化简：`B[j-1] ≤ A[i] 且 A[i-1] ≤ B[j]` ⇔ **在 `[0,m]` 上找最大的 i 满足 `A[i-1] ≤ B[j]`**（i 递增时 A[i-1] 递增、B[j] 递减，单调性成立 → 可二分）。

⚠️ 官方 Java 写 `min(index + half, len) - 1`，与自写 `min(index + half - 1, len - 1)` **等价**，只是 `-1` 位置不同。用户纠结「哪里该减一」时直接点破等价性，别陪着钻。

## 实测数据（Python 3.11，单次调用；N=1000000）

**轮数（确定性，首选证据）**

| m | n | 方法一 | 方法二 |
|---|---|---|---|
| 100万 | 100万 | 42 | 19 |
| 10万 | 10万 | 36 | 16 |
| 1000 | 1000 | 22 | 9 |
| 1000 | 100万 | 4 | 10 |
| 1 | 100万 | 2 | 2 |

**耗时（挂钟，μs，噪声大仅供量级参考）**：各 10 万 22.63 vs 14.66；各 100 万 31.20 vs **6.19**；1 vs 100 万 2.26 vs 2.74。

**反直觉点（写文章必配）**：
- 方法一 42 轮 ≈ 2×21 —— 偶数总长双调用，无法复用。
- `m << n` 时**方法一轮数反而极少**（短数组迅速耗尽 → 命中 `indx >= len` 提前返回），方法二 `log min(m,n)` 的理论优势根本体现不出来，耗时甚至略慢（0.82x）。
- 所以「方法二一定更快」是错的：它的优势区间是**两个数组都大且接近**。

## 验证脚本的三个坑（真实踩过，务必先自检口径）

1. **统计基准和被讨论的量不同口径** → 刷出海量假违规。
   LC4 里 `k` 是相对**剩余元素**的第几小，我却在**全局合并数组**上算排名，一次性产出 39761 条「违规」。
   修法：每轮用 `sorted(nums1[i:] + nums2[j:])` 作剩余集合再算排名。
2. **重复值 + `bisect_right`** → 同值元素被重复计数，把「值相同的位置本就等价」误判为违规。
   修法：验证「谁不可能是第 k 小」要按值口径，或直接用无重复值用例（`random.sample(range(...), m+n)`）。
3. **自己写进脚本的期望值没核对** → 把两个都正确的实现判成失败。
   曾把 `[1,3,8]+[2,7,9,10]` 的期望误标成 5.5（合并后 `[1,2,3,7,8,9,10]`，第 4 个 = **7.0**）。

> **验证器自身的错误比被测代码的错误更隐蔽：它伪装成「被测代码全错」。**
> 出现「失败率高得离谱」（如 50%+）时，先怀疑自己的度量口径，再怀疑被测代码。
